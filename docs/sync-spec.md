# 一句 · 多端同步规格（v3）

两端（Windows / Android）都按这一份实现，否则数据会互相写坏。

## 0. 为什么必须先改"身份"

同步之前，句子和列表的 id 是**各端自己生成的整型**（列表内 max+1）：

```csharp
Id = (l.Items.Count == 0 ? 0 : l.Items.Max(i => i.Id)) + 1
```

两端完全独立记账，后果是必然冲突：

```
手机端加了「不积跬步…」  → id = 15
电脑端加了「行胜于言。」  → id = 15     ← 同一个 id，两句完全不同的话
```

合并时按 id 对齐的话，一边的句子会被另一边顶掉；再加上没有时间戳，连"谁更新"都判断不了；
没有删除标记的话，某端删掉的句子下次同步又会被另一端"复活"。

所以每条数据必须有**跨设备稳定且唯一**的身份 + **时间戳** + **删除标记**。

## 1. 数据格式 v3

```json
{
  "v": 3,
  "deviceId": "win-3f9c…",
  "lists": [
    {
      "uuid": "a1f0c8b2-…", "n": "论语",
      "updatedAt": 1761712345678, "deleted": false,
      "items": [
        { "uuid": "e77a…", "t": "学而时习之，不亦说乎？", "s": "《论语·学而》",
          "updatedAt": 1761712345678, "deleted": false }
      ]
    }
  ]
}
```

| 字段 | 含义 | 说明 |
|---|---|---|
| `uuid` | 跨端唯一身份，**永久不变** | 新建时 `Guid.NewGuid()` |
| `t` / `s` | 句子正文 / 出处 | 沿用旧字段名，省一层映射 |
| `n` | 列表名 | |
| `updatedAt` | 最后修改时间，**Unix 毫秒** | 冲突就用它裁决 |
| `deleted` | 墓碑标记 | `true` 表示"已删除"，不能直接从文件里抹掉 |
| `id`（可选） | 旧版数字 id | **只为读老文件保留，读完即弃**，新文件不再依赖它 |

## 2. 稳定 UUID：让两端给同一条预置句算出同一个 uuid

.NET 没有 v5 UUID，两端自己实现同一个算法：

```
StableUuid(namespaceUuid, name):
    bytes = namespaceUuid 的 16 字节 || name 的 UTF-8 字节
    h     = SHA1(bytes)                      // 取前 16 字节
    h[6]  = (h[6] & 0x0F) | 0x50             // 版本号 5
    h[8]  = (h[8] & 0x3F) | 0x80             // RFC 4122 variant
    return UUID(h)
```

预置数据必须用这个算法生成，**命名空间和名字要写死一样**：

- 列表「论语」：`StableUuid(NS, "list:论语")`
- 第 i 条预置句（从 0 开始）：`StableUuid(NS, "preset:论语:" + i)`

这样两端装好就是同一批 uuid，第一次同步合并成 14 条 —— 而不是 28 条。

命名空间常量（Java 端写成 `UUID.fromString(...)`）：

```
NS = "6b5a1f3c-8d2e-4a7b-9c1d-0e2f3a4b5c6d"
```

### ⚠️ 字节序：.NET 与 Java 的 UUID 字节布局是**反的**

Windows 端最后一步是 `new Guid(bytes).ToString()` —— 而 .NET 的 `Guid`
**前三个字段是小端**（Java 的 `UUID` 全是大端）。所以：

- 喂给 SHA1 的"命名空间 16 字节"，.NET 侧实际是 `Guid.ToByteArray()` 的结果（小端）
- 输出时 .NET 打印的也是小端解释的那三个字段

Java 端必须**照样做一次字节换序**，才能打印出同一个字符串。实测（`name = "list:论语"`）：

| 实现 | 结果 |
|---|---|
| Windows（基准，已存进用户数据里） | `5cbd5673-d822-a659-84e1-4fadcc544464` ✅ |
| Java：命名空间转小端 + 输出前换序 | `5cbd5673-d822-a659-84e1-4fadcc544464` ✅ |
| Java：照 RFC 直写（不换序） | `7356bd5c-22d8-59a6-84e1-4fadcc544464` ❌ |
| Java：命名空间也用大端 | `4ff3f2bc-100c-4657-96a5-393c79ae3229` ❌ |

也就是说：**这不是标准 v5 UUID**，只是"两端一致"的确定性算法。改任何一端之前，
先拿上面这行基准值对一遍（验证脚本思路见 `%TEMP%\yiju_uuid2.ps1`）。

另一个参考值：`"preset:论语:0"` → `5df0179d-4a9b-e950-98e5-00ad8a1a1cf8`。

## 3. 合并规则

对每一层（列表、句子）分别合并，按 uuid 对齐：

1. 两端都有，且 `updatedAt` 不同 → **取时间戳大的**（最后写入者胜）
2. 两端都有，`updatedAt` 完全相同 → 按 `uuid` 字符串比较，小的那个胜（保证各端收敛到同一结果）
3. 只有一端有 → 直接采纳
4. 一端 `deleted=true`（墓碑）另一端有修改且**更新时间更晚** → 修改复活它
5. 墓碑保留 **30 天**后，各端可在自己落盘时彻底丢弃

合并结果一定是**幂等**的 —— 两台设备各跑一次，结果相同；并发覆盖写也能收敛。

## 4. 传输：WebDAV 单文件

远端就一个文件，实现最简单也最不容易出错：

```
https://dav.jianguoyun.com/dav/Yiju/yiju-sync.json
```

流程：

```
1) PROPFIND 拿 ETag（不存在则先 MKCOL 建目录）
2) GET     远端文件
3) merge(远端, 本地)   ← 按 §3
4) PUT     合并结果，带 If-Match: <ETag>（乐观锁）
5) 若返回 412 Precondition Failed → 说明别人刚写过，回到第 1 步重试（最多 3 次）
```

关于坚果云：

- 认证用 **Basic**：`Authorization: Basic base64(邮箱:应用密码)`。
  注意是**应用密码**，不是登录密码 —— 在坚果云网页端"账户信息 → 添加应用"里生成。
- 它支持 `PROPFIND / GET / PUT / DELETE / MKCOL`，HTTP 207/201/200/204 都验证过。
- 免费账户有流量限制，所以别高频上传：**内容变化后延迟 10 秒合并一次**，外加每 30 分钟一次兜底。

## 5. 不同步什么

| 数据 | 是否同步 | 原因 |
|---|---|---|
| 句子库（列表 + 句子） | ✅ 同步 | 真正的内容 |
| 每张卡片的位置/大小/配色 | ❌ 不同步 | 各设备屏幕不一样，同步过来只会错位 |
| 每张卡片的显示方式、游标 | ❌ 不同步 | 使用状态，不是内容 |

## 6. 迁移

两端都要做，顺序固定：

1. 读到旧格式（没有 `v` 或 `v < 3`）→ 逐条补 `uuid` / `updatedAt` / `deleted`
2. 预置数据按 §2 的**稳定 uuid** 生成，非预置数据用随机 uuid
3. `updatedAt` 取"文件最后修改时间"（没有读过磁记录就用当前时间）
4. 引用一并迁移：**原来的数字 id 引用要换成 uuid 引用**（卡片选的是哪个列表、固定句是哪一条）
5. 立刻落盘为 v3，之后按新格式运行

## 7. 实现记录（Windows 端已跑通，2026-10-29）

实测中出现过的两个坑，另一端照着抄的时候务必避开：

1. **坚果云的 `PROPFIND` 响应不带 `ETag` 头**，只有 `GET` 才返回（`Etag: 8_gp…`）。
   当初写成"PROPFIND 拿不到 ETag 就当远端不存在" → 每次启动都把本地覆盖上去，
   **另一端刚加的句子被直接抹掉**。现在：存在性只认 `GET` 是不是 404，
   ETag 只当**可选**的乐观锁（没有就不带 `If-Match`，靠合并的幂等性兜底）。
   `If-Match` 本身是生效的（拿错的 ETag 去 PUT 会返回 412）。
2. **"合并结果跟远端一字不差就别 PUT"**。否则会陷入
   "同步 → 触发保存 → 保存触发同步" 的空转，白耗坚果云的免费流量。

### 跨端一致性已在 CI 上验证（2026-10-29）

Android 端由 GitHub Actions 云构建（本机没有 JDK / Android SDK，编译不了），
所以把"两端算出的 uuid 必须一致"写成了**单元测试**，让 CI 把关：

- `app/src/test/java/com/fred/wordwidget/util/StableIdTest.kt`
  直接断言到 Windows 端**实际生成并存进数据文件**的值
  （`list:论语` → `5cbd5673-…`，`preset:论语:0/1/2` 三条）
- `app/src/test/java/com/fred/wordwidget/sync/MergeTest.kt`
  锁合并规则：两边各加的都要留着、最后写入者胜、墓碑不能被复活、换顺序结果一样

CI 日志里确认执行过（`Task :app:testDebugUnitTest`，非 SKIPPED）并 BUILD SUCCESSFUL，
即 **Java/Kotlin 侧算出来的 uuid 与 Windows 端严丝合缝**，字节序那个坑不用再担惊受怕。

另外两条经验：

- 预置数据才用稳定 uuid；用户自己建的列表用**随机** uuid —— 否则两端各建了个同名列表
  会被当成同一个合并掉，丢数据。
- 内容改动后**攒 10 秒**再传（外加每 30 分钟兜底），别一句一上传。
